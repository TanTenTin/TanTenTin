# Claude 작업 지침

## 작업 스타일

- 지시가 명확하면 설명 없이 바로 작업한다.
- 지시가 애매하거나 해석이 여러 갈래일 경우, 반드시 먼저 질문하고 확인 후 진행한다. 추측하지 않는다.
- 응답은 설명을 충분히 포함해서 상세하게 작성한다.

## 환경

- **OS**: Windows
- **터미널**: PowerShell
- 셸 명령어 작성 시 PowerShell 문법을 기준으로 한다. Bash 문법(`&&`, `$VAR` 등)을 사용하지 않는다.

## 기술 스택

- **언어 (선호)**: TypeScript, Python
- **언어 (사용 가능)**: PHP, C++, Java
- **프레임워크**: Next.js, Express, FastAPI
- **스타일링**: Tailwind CSS, CSS Modules
- **ORM / DB**: Prisma, TypeORM, MySQL, Elasticsearch
- **인프라**: Vercel, AWS

## 코딩 컨벤션

- 주석은 충분히 작성한다. 코드의 의도와 동작을 명확히 설명한다.
- 에러 처리는 꼭 필요한 곳에만 작성한다. 불필요한 방어 코드를 남발하지 않는다.

## Git 컨벤션

Conventional Commits 형식을 따른다. 커밋 메시지 본문은 한국어로 작성한다.

```
<type>: <한국어 설명>
```

**주요 타입**
- `feat`: 새로운 기능
- `fix`: 버그 수정
- `refactor`: 기능 변경 없는 코드 개선
- `chore`: 빌드, 설정 등 기타 작업
- `docs`: 문서 변경
- `test`: 테스트 추가 / 수정
- `style`: 코드 포맷 / 스타일 변경

## 테스트

- 테스트는 필요할 때만 작성한다. 모든 코드에 테스트를 강제하지 않는다.

## 문서화

- 인라인 docs보다 README 등 별개의 문서 파일을 우선한다.
- 코드 내 설명이 필요한 경우 주석으로 작성하고, 구조/사용법 설명은 별도 파일에 작성한다.

## 컨텍스트 관리

컨텍스트 비대화를 방지하기 위해 규칙을 세분화하고 paths 문법을 적극 활용한다.

### 원칙

- **이 파일(루트 CLAUDE.md)에는 프로젝트 전역 규칙만 작성한다.**
- 특정 디렉토리나 파일 유형에만 해당하는 규칙은 반드시 해당 위치의 `CLAUDE.md`로 분리한다.
- 규칙이 길어질 것 같으면, 먼저 분리할 위치를 고민하고 서브 파일부터 만든다.

### 서브디렉토리 CLAUDE.md 분리 기준

| 위치 | 담을 내용 |
|------|-----------|
| `src/api/CLAUDE.md` | REST 설계 원칙, 에러 응답 포맷, 인증 처리 방식 |
| `src/components/CLAUDE.md` | 컴포넌트 작성 규칙, props 네이밍, Tailwind 사용 패턴 |
| `src/db/CLAUDE.md` | 쿼리 작성 규칙, 마이그레이션 주의사항, ORM 사용 패턴 |
| `tests/CLAUDE.md` | 테스트 작성 규칙, 픽스처 관리, 커버리지 기준 |

### paths 문법 활용

하나의 CLAUDE.md 안에서도 특정 경로에만 규칙을 적용할 수 있다. 전역 파일을 나누기 애매한 경우에 사용한다.

```markdown
[!NOTE]
paths: src/api/**

- API 핸들러는 반드시 try-catch로 감싼다.
- 응답은 항상 { data, error } 구조로 반환한다.
```

```markdown
[!NOTE]
paths: **/*.test.ts, **/*.spec.ts

- describe → it 구조를 유지한다.
- 외부 의존성은 mock 처리한다.
```

### 체크리스트

새 규칙을 추가하기 전에 다음을 확인한다:

1. 이 규칙이 **모든 파일**에 적용되는가? → 루트 CLAUDE.md에 추가
2. 이 규칙이 **특정 디렉토리**에만 적용되는가? → 해당 디렉토리에 CLAUDE.md 생성 후 추가
3. 이 규칙이 **특정 파일 패턴**에만 적용되는가? → paths 문법으로 범위를 제한해서 추가
